# Performance Phase J Public-Read Limiter Strategy

> Date: 2026-06-18
> Scope: Planning only for public-read limiter strategy after Phase I exposed real backend 429s.
> Status: Strategy documented. No rate limits, app behavior, frontend fallback behavior, caching logic, database queries, auth, checkout, cart, orders, admin, uploads, reviews, CSRF, validation, sessions, or user logic were changed.

## Executive Summary

Phase I confirmed that the first medium-load failure is public-read limiter exhaustion, not backend API latency.

Current result:

- API smoke passed.
- API small passed.
- API medium failed with `59,215` backend 429s.
- Frontend website medium still showed `0` frontend-visible 429s because the frontend rendered fallback HTML with status `200`.

Phase J does not tune the limiter. It defines the strategy for Phase K so the next implementation does not blindly raise a single public bucket and accidentally weaken abuse protection.

## Traffic Types

### A. Browser Public Traffic

Browser public traffic comes from many real users and usually many client IPs.

Characteristics:

- Users request frontend pages, images, static assets, and sometimes public APIs.
- Static assets and images should mostly be served by CDN/image CDN.
- Browser public API calls should remain finite and abuse-protected.
- Real production browser traffic is distributed across many clients, unlike one local k6 IP.

Risk:

- A very high public API limit can invite scraping or automated catalog abuse.

### B. Next.js SSR Traffic

Next.js SSR traffic is generated by the frontend server when rendering pages.

Characteristics:

- Many users can cause the frontend server to call the backend.
- The backend may see these calls from a small number of frontend/server IPs.
- IP-based backend limits can exhaust even when the original browser traffic is legitimate.
- Vercel/Render/container deployments can concentrate SSR backend traffic through a small set of egress addresses.

Risk:

- Treating all SSR calls as one IP bucket can punish legitimate traffic.
- Blindly whitelisting frontend IPs can remove abuse controls if proxy/IP trust is wrong.

### C. Local k6 API Traffic

Local k6 API traffic is intentionally concentrated.

Characteristics:

- Many VUs call backend APIs from one local machine/IP.
- This is useful for exposing limiter behavior.
- It is not identical to real distributed browser traffic.
- It is also not identical to production SSR traffic, but it models concentrated backend pressure well.

Risk:

- Local medium failure does not prove production will fail at the same VU count.
- Local medium success would also not prove production can handle 1,000-5,000 users.

## Phase I Request Volume Estimate

The Phase I API script calls up to 7 backend public-read endpoints per iteration:

1. `GET /api/v1/homepage/full`
2. `GET /api/v1/products?limit=12&sort=newest`
3. `GET /api/v1/categories`
4. `GET /api/v1/brands`
5. `GET /api/v1/carousel`
6. `GET /api/v1/products/:slug` when a product slug exists
7. `GET /api/v1/products?limit=12&category=:slug` when a category slug exists

Setup also calls:

- `GET /api/v1/products?limit=12&sort=newest`
- `GET /api/v1/categories`

Observed k6 totals:

| Profile | HTTP requests attempted | Iterations | Backend 429s | Min remaining | Result |
| --- | ---: | ---: | ---: | ---: | --- |
| Smoke | 415 | 59 | 0 | 9585 | Passed |
| Small | 6,246 | 892 | 0 | 3339 | Passed |
| Medium | 62,554 | 8,936 | 59,215 | 0 | Failed |

Volume math:

- Smoke: `59 iterations * 7 API calls + 2 setup calls = 415 requests`.
- Small: `892 iterations * 7 API calls + 2 setup calls = 6,246 requests`.
- Medium: `8,936 iterations * 7 API calls + 2 setup calls = 62,554 requests`.

The public-read limit is currently `10,000` requests per 15 minutes in development and `5,000` requests per 15 minutes in production.

The smoke, small, and medium runs were executed in the same local 15-minute window. Because the same bucket was already partially consumed by smoke and small, medium started with about `3339` public-read requests remaining.

Approximate exhaustion point in the observed consecutive run:

- Medium produced `3,339` successful backend public-read responses and `59,215` failed `429` responses.
- Based on the k6 progress output, the bucket likely reached zero roughly 45-50 seconds into medium.
- That timing is specific to this consecutive local run because the bucket was already partially consumed.

Why small passed:

- Smoke plus small attempted `6,661` requests total.
- That stayed below the `10,000` development public-read bucket.
- Small ended with a minimum observed `rate_limit_remaining` of `3339`.

Why medium failed:

- Medium alone attempted `62,554` backend public-read requests.
- Even a fresh `10,000` request development bucket would be exhausted by that request count.
- In the observed run, medium started with only about `3339` remaining because smoke and small had already consumed the bucket.

## Current publicReadLimiter Behavior

Source files:

- `backend/src/middleware/rateLimiter.ts`
- `backend/src/middleware/publicReadRoutes.ts`
- `backend/src/app.ts`

Current limits:

| Environment | Public-read limit | Window |
| --- | ---: | --- |
| Development/test | 10,000 requests | 15 minutes |
| Production | 5,000 requests | 15 minutes |

Behavior:

- `publicReadLimiter` applies only to safe public `GET` and `HEAD` routes classified by `isPublicReadRequest`.
- It uses `express-rate-limit`.
- It uses Redis via `rate-limit-redis` when `redisClient` is available.
- Redis store prefix is `rl:public-read:`.
- If Redis is unavailable, the limiter falls back to the default in-memory store because `createRedisStore()` returns `undefined`.
- `passOnStoreError: true` keeps Redis errors from hard-failing requests.
- Standard rate-limit headers are enabled with `standardHeaders: true`.
- Legacy `X-RateLimit-*` headers are disabled with `legacyHeaders: false`.
- The key generator is the default `express-rate-limit` behavior because `publicReadLimiter` does not define a custom `keyGenerator`.
- In this app, `app.set('trust proxy', 1)` means `req.ip` can depend on the first trusted proxy.

Route coverage:

- `GET` / `HEAD /api/v1/products`
- `GET` / `HEAD /api/v1/products/*`
- `GET` / `HEAD /api/v1/categories`
- `GET` / `HEAD /api/v1/categories/*`
- `GET` / `HEAD /api/v1/brands`
- `GET` / `HEAD /api/v1/brands/*`
- `GET` / `HEAD /api/v1/carousel`
- `GET` / `HEAD /api/v1/homepage`
- `GET` / `HEAD /api/v1/homepage/full`

Bucket shape:

- All public-read routes share one public-read bucket per limiter key.
- One hot endpoint can exhaust capacity for all public-read endpoints for the same key.
- Auth, checkout, cart, admin, upload, review mutation, and other sensitive routes do not use this public-read bucket.

## Strategy Options

### Option A - Simply Raise publicReadLimiter

Description:

- Increase the current single public-read bucket.

Pros:

- Simple to implement.
- Medium may pass if the new limit is above the attempted request volume.
- Low code complexity.

Cons:

- Increases scraping and automated catalog abuse risk.
- Does not distinguish SSR traffic from direct browser/API traffic.
- Allows one endpoint to consume the full public-read budget.
- May hide real scaling problems instead of reducing request volume or improving traffic classification.

Assessment:

- Not recommended as the only Phase K change.
- It may be part of the solution only if made environment-configurable, finite, monitored, and paired with route-specific or SSR-aware controls.

### Option B - Route-Specific Public-Read Buckets

Description:

- Split public reads into separate finite buckets by route family.

Example buckets:

- `homepage/full`
- `products list/search`
- `product detail`
- `categories`
- `brands`
- `carousel`

Pros:

- Prevents one endpoint from exhausting all public reads.
- Allows cheap/reference endpoints such as categories, brands, and carousel to have different limits from product list/search.
- Safer than one huge bucket.
- Easier to reason about when k6 identifies which endpoint family is hot.

Cons:

- More limiter configuration.
- More tests needed for route classification.
- Still IP-based unless paired with SSR-aware keying.
- Too many buckets can become difficult to operate.

Assessment:

- Recommended as part of Phase K.
- Keep the buckets finite and environment-configurable.

### Option C - Internal SSR Limiter Using Server-Only Secret

Description:

- Next.js server-side code sends an internal header to the backend.
- The header contains a secret stored only in server environment variables.
- Backend verifies the secret.
- Verified SSR requests use a separate finite SSR public-read bucket.
- Browser/client requests never receive or send the secret.

Pros:

- Safer than IP whitelisting.
- Handles frontend server/backend traffic concentration.
- Lets SSR traffic have a separate finite budget from direct browser API traffic.
- Works better for platforms where the frontend has a small number of backend egress IPs.

Cons:

- Requires careful secret handling.
- Secret must never be exposed through `NEXT_PUBLIC_*` variables or client bundles.
- Backend must reject missing/invalid SSR secrets from the SSR bucket.
- SSR bucket must remain finite and monitored.

Assessment:

- Recommended for Phase K design if implementation can be kept narrow.
- Do not make the SSR bucket unlimited.

### Option D - Signed Original-Client Key

Description:

- Frontend signs original client identity data with HMAC.
- Backend verifies signature.
- Limiter key becomes original-client-aware for SSR requests.

Pros:

- Closer to real per-user/per-client limiting.
- Avoids all SSR users sharing one frontend server IP bucket.

Cons:

- More complex.
- Requires careful proxy/header trust.
- High risk if `X-Forwarded-For` or similar headers are blindly trusted.
- Bugs can create spoofing or bypass risks.

Assessment:

- Not recommended for immediate Phase K unless there is a strong deployment-specific reason.
- Consider only after provider proxy behavior and trusted headers are fully documented.

### Option E - CDN/Edge Protection Plus Higher Backend Public-Read Limits

Description:

- Use CDN/WAF/bot controls to block abusive public-read traffic before it reaches the backend.
- Keep backend public-read limits higher but still finite.

Pros:

- This is closer to real production architecture.
- Blocks obvious scraping and abusive traffic earlier.
- Reduces backend pressure from static assets, images, and repeated cacheable reads.

Cons:

- Depends on deployment provider.
- Local tests cannot fully model CDN/WAF behavior.
- Requires staging/production configuration and monitoring.

Assessment:

- Recommended for production/staging planning.
- Not sufficient as a local code-only Phase K change.

## Recommended Phase K Direction

Recommended implementation sequence:

1. Keep all sensitive limiters strict and unchanged.
2. Make public-read limits environment-configurable with conservative defaults.
3. Split public-read traffic into a small set of route-specific finite buckets.
4. Add a separate verified internal SSR public-read bucket using a server-only secret.
5. Keep direct browser/public API traffic under finite public-read route buckets.
6. Keep rate-limit headers exposed for measurement.
7. Continue pairing backend API k6 and frontend website k6.

Recommended bucket model:

| Bucket | Purpose | Notes |
| --- | --- | --- |
| Direct public homepage | Browser/API calls to homepage public data | Finite, route-specific |
| Direct public product list/search | Browser/API product list reads | Finite, stricter than static metadata |
| Direct public product detail | Browser/API product detail reads | Finite |
| Direct public metadata | Categories, brands, carousel | Finite, likely higher than product search |
| Verified internal SSR public-read | Frontend server rendering calls | Finite, server-secret protected |

Important non-goals:

- Do not IP-whitelist the frontend.
- Do not blindly trust `X-Forwarded-For`.
- Do not create an unlimited public bucket.
- Do not weaken auth, checkout, cart, admin, upload, review, CSRF, validation, sessions, or user protections.
- Do not expose the SSR secret to browser JavaScript.

## Security Risks

Main risks:

- Raising public limits too high can invite scraping.
- A shared public bucket lets one endpoint starve other public reads.
- IP whitelisting can become a bypass if proxy trust is wrong.
- Trusting unverified forwarded headers can let clients spoof identity.
- An SSR secret in a `NEXT_PUBLIC_*` variable would be exposed to browsers.
- A missing/invalid SSR secret must never fall through to SSR privileges.
- A separate SSR bucket must still be finite and monitored.

Mitigations:

- Keep limits finite.
- Keep limits environment-configurable.
- Validate route classification with tests.
- Verify SSR secret server-side only.
- Keep direct public browser traffic separate from verified SSR traffic.
- Monitor 429 counts by bucket and route family.
- Use CDN/WAF controls for production abuse protection.

## Phase K Acceptance Criteria

Phase K should pass only when:

- API smoke passes.
- API small passes.
- API medium has 0 backend 429s, or expected backend 429s are explicitly documented for a deliberately abusive profile.
- Frontend website medium documentation no longer treats frontend `200` pages as proof that backend public APIs avoided 429s.
- Sensitive limiter tests still pass.
- Auth, cart, checkout, admin, upload, review, CSRF, validation, sessions, and user protections remain unchanged.
- Public-read route classification tests pass.
- Public-read abuse risk is documented.
- Rate-limit headers remain observable for k6/API validation.

Phase K must not claim 1,000-5,000 concurrent-user support. That remains staging/production-like validation work.

## Tests Needed For Phase K

Recommended backend tests:

- Public-read route classification covers all intended safe `GET`/`HEAD` routes.
- Public-read route classification excludes unsafe methods.
- Auth routes do not use public-read privileges.
- Cart, checkout/orders, admin, uploads, review mutations, CSRF-protected, session/user routes remain under their existing protections.
- Route-specific limiter behavior works if implemented.
- One route bucket does not exhaust unrelated route buckets if route-specific buckets are chosen.
- Internal SSR secret validation works if implemented.
- Missing SSR secret does not use the SSR bucket.
- Invalid SSR secret does not use the SSR bucket.
- Browser/client requests cannot access internal SSR privileges.
- Rate-limit headers are present for public-read API validation.

Recommended k6 tests:

- `PROFILE=smoke` API public-read.
- `PROFILE=small` API public-read.
- `PROFILE=medium` API public-read.
- Frontend website medium.
- Record backend 429 count, rate-limit remaining minimum, p95, p99, and slowest endpoint family.

Recommended manual/staging checks:

- Verify SSR secret is present only in server environment variables.
- Verify no `NEXT_PUBLIC_*` variable contains internal SSR secrets.
- Verify CDN/WAF strategy before any production limit increase.

## Phase J Conclusion

The next phase can start, but it should not be a blind public-read limit increase.

Recommended Phase K:

- Introduce environment-configurable finite limits.
- Add route-specific public-read buckets.
- Add a separate verified internal SSR public-read bucket if the secret can be kept server-only.
- Keep sensitive protections unchanged.
- Re-run API smoke, API small, API medium, and frontend website medium.
